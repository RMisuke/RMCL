# 插件系统价值与移除收益分析（2026-10-28）

- **范围**：RMCCC 自研插件系统（`rmccc-plugin` / `rmccc-logic` / `src-logic-host` / 18 条插件 IPC /
  隔离 UI / 主题 v1–v2 / SDK / 示例 / 相关文档）。
- **不包含**：Tauri 官方插件（`tauri-plugin-updater` / `window-state` / `dialog` / `process` / `opener`）
  与构建期插件，这些与 RMCCC 插件系统无关，移除本报告讨论的插件系统不会影响它们。
- **方法**：源码盘点、依赖/打包检查、现有审计结论复核；**未做**“去插件构建”对照实验，因此二进制
  体积归因是估算值（见 §8）。

---

## 0. 结论（先看这段）

1. **今天的插件系统并没有兑现“生态”，主要兑现的是“主题”**：逻辑插件 helper 没有打进 `.app`；
   Windows 的隔离 UI 被安全门禁关闭；没有签名、没有远程目录、没有市场；安装只能选本地 `.rmcpkg`。
2. **完整移除（连主题一起）会去掉刚做完的主题 v2**，与“像 DeepSeek Harness 一样靠主题插件做启动器”
   的产品方向冲突；只在“主题不再是卖点”时推荐。
3. **推荐“方案 B：去掉执行型插件，把主题降级为本地一等外观包”**：
   删除包安装/权限/注册表/隔离 UI/WASM/桥/SDK/插件页，保留并简化主题加载与校验。
   这能消掉绝大部分攻击面与维护成本，同时保住 Aurora / Grass / Midnight 和特效系统。
4. **建议保留（方案 D）只在一种情况下成立**：愿意投入 ADR-008 签名/目录 + Windows 容器 +
   审核流程，把插件当生态做。否则“半套插件系统”是纯负债。

（详见 [`PLUGIN_SECURITY_AUDIT_2026-10-27.md`](PLUGIN_SECURITY_AUDIT_2026-10-27.md)）。

## 2. 今天实际可用的能力（不是设计目标）

| 能力 | 实际状态 | 备注 |
|---|---|---|
| 主题 v1（8 色） | ✅ 可用 | 安装、列表、应用、安全色隔离 |
| 主题 v2（字体/圆角/间距/背景视频/组件/特效） | ✅ 可用（macOS） | 新增 `themes.skin` 授权；Aurora/Grass 示例已验证 |
| 声明式卡片/设置页 | ✅ 可用 | 宿主绘制；未安装任何示例时体感为 0 |
| 隔离 UI 卡片 | ✅ macOS；⛔ Windows | Windows 直接不生成 `uiUrl`（wry 子帧 IPC 风险） |
| 逻辑插件（WASM） | ⚠️ 代码在，helper 不在 `.app` | 生产包内没有 `rmccc-logic-host`，调用会失败 |
| 插件分发/签名/市场 | ❌ 未实现 | ADR-008 仍 proposed；只能本地选包 |
| 插件生态 | ❌ 无真实第三方 | 只有仓库内示例 |

> 这一点决定收益判断：**移除插件系统“损失”的主要是主题**，而不是一个正在运转的生态。

## 3. 移除的收益

### 3.1 安全与合规（最大收益）

去掉以下整类风险，而不是逐条加固：

- 第三方包解析/解压（zip slip、zip bomb、symlink、大小/压缩比）；
- 安装事务、注册表、权限授予/撤销/审计、升级权限扩张；
- 隔离 UI（自定义 scheme、CSP、资源白名单、postMessage 桥、导航封印、iframe 同源问题）；
- Host Bridge（`network.request` SSRF、`llm.chat`、`settings.get`/`instances.list` 数据面）；
- WASM helper（独立进程、fuel/内存限制、import 白名单）与逻辑插件命令；
- 主题资产路由（`rmcccplugin://`、字体 CORS、视频 Range、SVG 清洗）；
- 未签名安装的供应链风险（F-04）与 Windows 隔离 UI release blocker（F-02）。

安全审计、发布检查、跨平台验证的工作量随之消失；威胁模型回到“本地启动器 + 用户自己的文件”。

### 3.2 复杂度与维护

- 主程序减少 **12,000+ 行 Rust**、**18 条 IPC**、**约 1,100 行前端**、**约 130 条测试**；
- 少 3 个 workspace crate（plugin/logic/logic-host）与一个 helper 构建产物；
- 少 6 份 ADR、2 份指南、1 份平台架构指南、1 个 SDK、1 套 schema 的同步维护；
- 少一条“安装 → 审查 → 启用 → 配置 → 升级 → 回滚”的状态机与对应 UI 文案；
- 新功能不必再考虑“插件 API 兼容/权限/沙箱”，直接做内置功能，迭代更快。

### 3.3 可靠性与体验

- 不再有插件注册表损坏、权限待审、插件崩溃/iframe 白屏、主题资产 404、版本回滚等故障面；
- 设置项减少（插件页、插件宿主、权限对话框、安装包选择）；
- 主题不再需要“安装插件 + 授予 themes.skin + 启用”三步，可直接在内置外观页选择/导入；
- 启动时不再扫描插件目录/解析注册表/读取主题资产（预计收益为毫秒级，未实测）。

### 3.4 体积与构建

- 可删掉 helper（1.1 MiB）与 `wasmi` 依赖链（本来就没打包，但仍在 workspace/CI 构建）；
- 主可执行预计减少 **0.4–0.9 MiB**（`zip` 解压、权限/注册表、桥协议、主题资产校验等）；
  对 9.5 MiB 的体量不是决定性收益，**体积不是主要理由**；
- 编译单元/测试/CI 时间下降（未实测）。

### 3.5 跨平台

- 不再需要解决 Windows WebView2 子帧 IPC 问题，也不再需要 Linux 隔离 UI 实测；
- 插件 UI 的“macOS-only + Windows 关闭”这一产品割裂消失。

---

## 4. 移除的代价与风险

1. **主题自定义能力**：如果连主题一起删，用户只剩 8 套内置主题；刚完成的 v2（字体/视频/特效）
   与 Aurora/Grass/Midnight 全部失效。
2. **扩展性/差异化**：失去“像 DSH 一样靠插件扩展”的产品叙事、SDK、第三方生态与 ADR-008 分发路线。
3. **迁移成本**：
   - `CoreContext.plugin_manager` 被主题解析、卡片、设置页依赖；
   - 18 条 IPC、插件页/路由/i18n、CLI `plugin` 子命令、MCP/文档需要清理；
   - 已安装插件的用户需要迁移/导出主题，否则升级后主题消失；
   - 插件相关 ADR（003/004/006/007/008/014）需要 superseded，审计/指南重写。
4. **沉没成本**：Phase 2/4/5/7 的实现、SDK、示例、审计与文档投入无法回收（决策时不应被沉没成本绑架，
   但需要如实告知）。
5. **未来需求受限**：卡片/逻辑/AI 扩展若再想做，只能内置，或重新引入插件系统。

## 5. 方案对比

| 方案 | 第三方代码 | 主题 | 主程序体积 | 攻击面 | 迁移工作量 | 生态 |
|---|---|---|---|---|---|---|
| **A. 全量移除（含主题）** | 无 | 仅内置 8 套 | 最小 | 最低 | 中 | 无 |
| **B. 去执行型插件，主题降级为本地外观包**（推荐） | 无 | 保留 v1/v2 + 本地导入 | 小（−0.4–0.9 MiB） | 大幅降低 | 中 | 无（但保留外观扩展） |
| **C. 只保留声明式包（主题+卡片），删 UI/logic/桥** | 无 | 保留（包形式） | 中 | 中 | 中低 | 有限 |
| **D. 保留现状/补完生态** | 有 | 保留 | 最大 | 最高 | 0（但持续维护） | 可能 |

- **A** 适合“启动器只做启动，不要外观扩展”。
- **B** 适合“主题是卖点，但不做第三方代码生态”——把主题从“插件”变成“外观包”，
  保留 v2 的字体/视频/特效，删除安装/权限/注册表/UI/WASM/桥。
- **C** 适合“还想要第三方卡片，但不执行代码”——仍需保留包安装/Manifest/权限（低风险能力），
  收益小于 B。
- **D** 只有在愿意投入签名/目录/审核/Windows 容器时才成立；否则是半成品负债。

## 6. 推荐：方案 B（分步）

**目标形态**：`themes/`（用户目录）下放主题 JSON + `assets/`，应用启动扫描；沿用现有
`ThemeDocument` / `theme_assets` / `ThemeSkin` 校验；不再有 `.rmcpkg`、权限、注册表、iframe、WASM。

1. **冻结**：停止扩展插件 API/分发；在文档标注 deprecated。
2. **迁移主题代码**：把 `theme.rs` / `theme_assets.rs` / `skin.rs` 移到 `rmccc-dashboard`
   （或独立 `rmccc-appearance`），去掉对 `PluginManager` 的依赖；主题 key 从 `<pluginId>/<themeId>`
   改为本地文件 id；`themes.skin` 能力门槛删除（本地文件仍做同样的安全校验）。
3. **新命令**（约 3–5 条）：`themes_list` / `themes_get_tokens` / `themes_get_skin` /
   `themes_set_preference` / `themes_import`（可选）。替换现有 5 条 dashboard 主题命令。
4. **删除**：`rmccc-plugin`（除主题模块）、`rmccc-logic`、`src-logic-host`、18 条插件 IPC、
   `plugin.rs` / `plugin_ui.rs` / `plugin_logic.rs`、Plugins 页/路由/`plugin-ui`/`stores/plugins`、
   Settings 插件宿主、SDK、manifest/UI bridge schema、示例卡插件；移除 `CoreContext.plugin_manager`。
5. **迁移用户数据**：首次启动把 `plugins/*/themes/*.json` + `assets/` 复制到 `themes/`；
   无法迁移的（UI 卡/逻辑插件）给出一次性说明；保留回滚点。
6. **文档**：ADR-003/004/006/007/008/014 superseded/重写；安全审计关闭；主题指南改为“外观包”。
7. **验收**：主题导入/切换/撤销、v2 资产校验负向用例、无插件时的启动/设置/主页截图、
   二进制与启动时间对比。

**工作量估算**：代码删除/搬迁 + 主题加载重构约 **2–4 个工程师日**；加迁移、UI、文档、回归
约 **1–2 周**。风险主要是已安装主题的迁移与 `CoreContext`/dashboard 的耦合。

如果选 **A**：在 B 基础上再删主题 v2 的皮肤层（字体/背景/特效/组件）、资产路由与相关 CSS，
只保留 8 套内置主题；额外约 2–3 天，但会失去本轮主题能力。

---

## 7. 保留（D）的前提条件

若决定继续做插件生态，最低门槛：

1. ADR-008 落地（签名 + 可信目录 + 撤回），否则“安装即完全信任”不可接受；
2. Windows 隔离 UI 解决（frame-sealed 容器或 Tauri 修复）并实测；
3. logic helper 真正打包进 `.app`（当前没有）；
4. 有审核/举报/下架流程与 API 兼容承诺；
5. 接受长期安全审计与跨平台测试成本。

达不到以上条件，建议不要维持“完整插件系统”的复杂度。

---

## 8. 度量局限

- 未构建“去插件”对照二进制，**0.4–0.9 MiB 是估算**；若需要精确值，可做一次
  临时 worktree 删除插件命令/crate 后 `cargo build --release` 对比（约 10 分钟）；
- 未测启动耗时、内存、CI 时间；
- 未统计真实第三方插件使用率（当前没有分发渠道，无法统计）；
- LOC 含测试与空行，仅用于量级比较。

---

## 9. 需要拍板的问题

1. 主题（含 v2 特效）是否仍是产品卖点？
   - 是 → 选 **B**；否 → 选 **A**。
2. 是否需要第三方卡片/逻辑扩展？
   - 需要 → 只能选 **D**（并补签名/Windows/打包），或 **C**（仅声明式卡片）。
3. 是否接受“本地外观包”取代“插件安装”的 UX（无权限审查、无版本市场）？
4. 已安装插件/主题的迁移策略：自动导入、导出后清空，还是保留只读？
